# SQLite Database Schema

## Purpose

The AgIR SQLite database is the durable control plane for storage inventory and
pipeline orchestration. It records what files exist, what batches are ready,
which inputs have been staged, which compute submissions are active, and what
stage runs have completed.

The canonical schema is defined in:

```text
schemas/sqlite/pipeline.sql
```

The current schema version is `4`.

For the complete runtime flow, see
[`SQLITE_ORCHESTRATOR_ARCHITECTURE.md`](SQLITE_ORCHESTRATOR_ARCHITECTURE.md).
For day-to-day commands, see [`OPERATOR_RUNBOOK.md`](OPERATOR_RUNBOOK.md).

## Schema Overview

The database contains three groups of objects:

| Group | Objects | Purpose |
| --- | --- | --- |
| Inventory | `inventory_runs`, `globus_file_index` | Track storage scans and current file state |
| Reporting | `batch_inventory_summary`, `storage_gap_summary` | Store per-scan aggregate counts |
| Orchestration | `stage_runs`, `stage_leases`, `staged_inputs` | Track execution, concurrency, and prerequisite transfers |
| Readiness | `v_batches_needing_raw_to_jpg`, `v_batches_needing_jpg_to_det`, `v_batches_needing_det_to_world` | Calculate batches eligible for pipeline stages |

## Logical Relationships

```text
inventory_runs
    |
    +--< globus_file_index
    |
    +--< batch_inventory_summary
    |
    +--< storage_gap_summary

globus_file_index ----------------------+
                                        |
stage_runs -----------------------------+--> readiness views
                                        |
stage_leases ---------------------------+

staged_inputs -- completed batch/stage --> compute-submission gate

stage_leases -- lease_id --> generated Slurm job
stage_runs   -- run_id   --> run_report.json
```

The inventory summary tables have declared foreign keys to `inventory_runs`.
The orchestration tables relate through `batch_id` and `stage`, but those
relationships are intentionally logical rather than foreign-key constrained.
This allows inventory, staging, leases, and run history to be written at
different points in the lifecycle without requiring a central batch table.

## Storage Conventions

### Identifiers

- Inventory scan IDs are integer values generated by SQLite.
- File IDs are integer values generated by SQLite.
- Stage run IDs are UUID strings supplied by `run_report.json`.
- Lease IDs and staging IDs are UUID strings generated by the orchestrator.
- Batch IDs are text values such as `MD_2025-04-25`.

### Dates and timestamps

Dates and timestamps are stored as ISO-8601 `TEXT`. Most generated timestamps
use UTC and a trailing `Z`, for example:

```text
2026-07-15T14:30:00Z
```

Keeping timestamps in a consistent, zero-padded UTC representation allows the
schema to compare lease expiration values lexically.

### Boolean values

SQLite integers represent booleans:

```text
0 = false
1 = true
```

Columns using this convention have `CHECK` constraints restricting them to
`0` or `1`.

### JSON

The complete stage run report is retained in `stage_runs.run_report_json` as
serialized JSON text. Frequently queried fields are also stored in dedicated
columns.

## Inventory Tables

### `inventory_runs`

One row represents one crawl of a storage scope. A scope is identified by its
endpoint, storage root, and data state, with site, storage domain, and namespace
providing additional classification.

Primary key:

```text
run_id
```

Important columns:

| Column | Meaning |
| --- | --- |
| `run_id` | Integer scan identifier |
| `endpoint` | Globus endpoint ID |
| `site` | Physical site label |
| `storage_domain` | Logical storage ownership/domain |
| `namespace` | Logical namespace within the domain |
| `storage_root` | Root path scanned by the inventory command |
| `data_state` | Pipeline data-state classification |
| `started_at_ts_iso` | Scan start time |
| `ended_at_ts_iso` | Scan end time |
| `status` | Current or terminal scan state |
| `total_seen` | Total entries observed |
| `total_files_seen` | Files observed |
| `total_dirs_seen` | Directories observed |
| `total_batches_written` | Batch summaries written |
| `total_errors` | Errors encountered during the scan |
| `total_marked_stale` | Previously current rows marked missing |
| `error_summary` | Optional failure summary |

Valid statuses:

```text
running
success
partial
failed
skipped
```

Write owner:

```text
scripts/admin/globus_index.py
```

### `globus_file_index`

Stores one row for each file or directory discovered across configured storage
endpoints. This is the authoritative inventory used by the readiness views.

Primary key:

```text
file_id
```

Natural uniqueness constraint:

```text
(endpoint, data_state, storage_root, rel_path)
```

Important column groups:

#### Storage location

| Column | Meaning |
| --- | --- |
| `endpoint` | Globus endpoint containing the entry |
| `site` | Physical site label |
| `storage_domain` | Logical storage ownership/domain |
| `namespace` | Logical namespace |
| `storage_root` | Indexed root path |
| `rel_path` | Path relative to the indexed root |
| `full_path` | Complete endpoint path |
| `parent_dir` | Immediate parent directory name |
| `file_name` | File or directory name |

#### File classification

| Column | Meaning |
| --- | --- |
| `entry_type` | `file` or `dir` |
| `file_ext` | Extension without a leading dot |
| `size_bytes` | Entry size where available |
| `permissions` | Permission text returned by the scanner |
| `checksum` | Optional checksum value |

#### Batch classification

| Column | Meaning |
| --- | --- |
| `batch_id` | Parsed batch identifier |
| `batch_state` | State prefix parsed from the batch ID |
| `batch_date` | Date parsed from the batch ID |
| `data_state` | Pipeline storage state such as `semifield-upload` |

#### Inventory history

| Column | Meaning |
| --- | --- |
| `first_seen_ts_iso` | First time the scanner observed the entry |
| `last_seen_ts_iso` | Most recent observation time |
| `last_seen_run_id` | Inventory run that most recently observed it |
| `missing_since_ts_iso` | Time it was first found missing |
| `is_current` | Whether it was present in the latest scan of its scope |

Current entries use:

```text
is_current = 1
missing_since_ts_iso IS NULL
```

When an entry is absent from a later scan of the same scope, the scanner sets
`is_current = 0` and records `missing_since_ts_iso`. Historical rows are kept
instead of being deleted during normal scans.

Write owner:

```text
scripts/admin/globus_index.py
```

## Reporting Tables

The reporting tables are derived snapshots associated with inventory runs.
They support inspection and dashboards but do not drive the readiness views.

### `batch_inventory_summary`

Stores per-run, per-scope, per-batch aggregates.

Composite primary key:

```text
(run_id, endpoint, site, storage_domain, namespace,
 storage_root, data_state, batch_id)
```

The table records:

- file and directory counts;
- total file size;
- counts by important extension;
- metadata and detection counts; and
- minimum and maximum modification timestamps.

`run_id` references `inventory_runs.run_id`.

Write owner:

```text
scripts/admin/globus_index.py
```

### `storage_gap_summary`

Stores a per-run view of which data states exist for each batch and storage
scope.

Composite primary key:

```text
(run_id, batch_id, storage_domain, namespace, site, storage_root)
```

The table records presence flags and counts for:

- uploaded source data;
- developed images;
- cutouts;
- RAW files;
- JPG files;
- metadata;
- detections; and
- cutout PNG files.

`run_id` references `inventory_runs.run_id`.

Write owner:

```text
scripts/admin/globus_index.py
```

## Orchestration Tables

### `staged_inputs`

Tracks the lifecycle of inputs moved to the compute environment before job
submission. The compute-submission gate requires a completed row for the
selected batch and stage.

Primary key:

```text
staging_id
```

Natural uniqueness constraint:

```text
(batch_id, stage, src_path, dst_path)
```

Important columns:

| Column | Meaning |
| --- | --- |
| `staging_id` | UUID for the request |
| `batch_id` | Batch whose inputs are moving |
| `stage` | Stage that will consume the inputs |
| `src_endpoint` | Source Globus endpoint |
| `dst_endpoint` | Destination Globus endpoint |
| `src_path` | Source path |
| `dst_path` | Destination path |
| `status` | Current request state |
| `requested_by` | Operator or command identifier |
| `priority` | Ordering value; lower values are returned first |
| `globus_task_id` | Remote transfer task identifier |
| `error_summary` | Terminal error information |
| `requested_at` | Initial or reopened request time |
| `submitted_at` | First submitted, active, or completed timestamp |
| `completed_at` | First terminal timestamp |
| `updated_at` | Most recent row update time |

Valid statuses:

```text
planned
requested
submitted
active
completed
failed
canceled
```

Normal successful lifecycle:

```text
requested -> submitted -> active -> completed
```

`stage_inputs.py --dry-run` reports planned work without writing a row. New
persisted rows begin as `requested`. A matching active or completed request is
returned without creating a duplicate. A failed or canceled request can be
reset to `requested` and submitted again.

Writers:

```text
scripts/job/stage_inputs.py
scripts/job/poll_stage_inputs.py
orchestrator/sqlite_db.py
```

Reader:

```text
scripts/job/submit.py
```

### `stage_leases`

Provides one active submission lease for each batch and stage. Leases prevent
two orchestrator processes from submitting the same unit of work at the same
time.

Primary key:

```text
lease_id
```

Uniqueness constraint:

```text
(batch_id, stage)
```

Important columns:

| Column | Meaning |
| --- | --- |
| `lease_id` | UUID identifying the lease |
| `batch_id` | Leased batch |
| `stage` | Leased pipeline stage |
| `orchestrator_id` | Process identity that owns the lease |
| `claimed_at` | Claim time |
| `expires_at` | Time after which another submission may replace it |
| `slurm_job_id` | Scheduler job ID recorded after successful submission |

`claim_stage_lease()` uses `BEGIN IMMEDIATE` so the read-check-write operation
is serialized across competing SQLite writers. An active unexpired lease
causes a lease conflict. An expired lease is deleted and replaced.

Lease release deletes the row and verifies `orchestrator_id` ownership. Calling
release again is safe and reports that no row was removed.

Writers:

```text
orchestrator/submit_jobs.py
scripts/job/ingest_and_release.py
orchestrator/sqlite_db.py
```

### `stage_runs`

Stores the durable result of each pipeline-stage execution.

Primary key:

```text
run_id
```

Important column groups:

#### Run identity and result

| Column | Meaning |
| --- | --- |
| `run_id` | UUID supplied by `run_report.json` |
| `batch_id` | Processed batch |
| `stage` | Executed stage |
| `stage_version` | Stage implementation version |
| `status` | Normalized terminal status |
| `exit_code` | Stage exit code |
| `started_at` | Stage start time |
| `ended_at` | Stage end time |
| `duration_ms` | Execution duration |

Valid statuses:

```text
success
partial_success
failed
canceled
skipped
```

#### Provenance

| Column | Meaning |
| --- | --- |
| `code_commit` | Source revision recorded by the stage |
| `config_path` | Stage configuration path |
| `config_hash` | Configuration content hash |
| `model_id` | Model identifier where applicable |

#### Input and output summary

| Column | Meaning |
| --- | --- |
| `input_root` | Root input location |
| `n_units_discovered` | Work units found by the stage |
| `n_units_succeeded` | Work units completed successfully |
| `n_units_failed` | Work units that failed |

#### Artifact pointers

| Column | Meaning |
| --- | --- |
| `run_root` | Directory containing the ingested report |
| `artifacts_dir` | Stage artifact directory |
| `manifest_path` | Optional manifest location |
| `logs_path` | Optional logs location |
| `run_report_json` | Complete serialized run report |
| `ingested_at` | Database ingestion time |

`ingest_run_report()` uses an upsert on `run_id`. Re-ingesting a report updates
its result, counts, paths, and stored JSON instead of adding a duplicate row.

Writers:

```text
scripts/job/ingest_and_release.py
orchestrator/sqlite_db.py
```

## Readiness Views

Readiness views calculate work directly from current `globus_file_index` rows.
They do not use the reporting summary tables and are not restricted to one
inventory run. This allows current inventory from multiple endpoints and scan
times to participate in one readiness decision.

Both views exclude a batch when:

- the expected output files already exist;
- an unexpired lease exists for the batch and stage; or
- `stage_runs` contains a successful run for the batch and stage.

Input-transfer completion is a separate gate applied by `submit.py` after it
queries a readiness view.

### `v_batches_needing_raw_to_jpg`

Returns batches that have current RAW input files but no current JPG files in
an `images` directory.

Output columns:

| Column | Meaning |
| --- | --- |
| `batch_id` | Ready batch |
| `batch_date` | Earliest batch date found in inventory |
| `raw_file_count` | Current RAW inputs |
| `jpg_file_count` | Current JPG outputs; expected to be zero |

The view excludes active `raw_to_jpg` leases and successful `raw_to_jpg` runs.

### `v_batches_needing_jpg_to_det`

Returns batches that have current JPG inputs in an `images` directory —
anywhere, any site — but no current detection-related files. `jpg_to_det`
resolves the actual transfer source via the same destination/CERES/JUNO
priority chain `det_to_world` uses (see
`orchestrator/input_staging_planner.py`'s `_plan_multi_site_requests`), so
this view isn't restricted to a fixed set of sites.

Output columns:

| Column | Meaning |
| --- | --- |
| `batch_id` | Ready batch |
| `batch_date` | Earliest batch date found in inventory |
| `jpg_count` | Current JPG inputs |
| `det_count` | Current detection outputs; expected to be zero |

Detection output is identified through the `detections`,
`plant-detections`, and `metadata` parent directories. The view excludes active
`jpg_to_det` leases and successful `jpg_to_det` runs.

### `v_batches_needing_det_to_world`

Returns batches that have current detection files, current developed-image
files, AND current pixel-to-world NPZ grids (`semifield-asfm`,
`pixel_world_grids` parent dir) — anywhere, any site — with no current
georeferenced output yet.

Output columns:

| Column | Meaning |
| --- | --- |
| `batch_id` | Ready batch |
| `batch_date` | Earliest batch date found in inventory |
| `img_count` | Current developed-image inputs |
| `det_count` | Current detection inputs |
| `grid_count` | Current pixel-to-world NPZ grid inputs |
| `georef_count` | Current georeferenced outputs; expected to be zero |

Unlike the two views above, this does **not** gate on locality — it answers
"does this batch's data exist somewhere so `det_to_world` could run", not
"is it staged on the compute cluster". The actual submission/locality gate
is `scripts/job/submit.py`'s `filter_det_to_world_staged_ready()`, which
checks `staged_inputs` directly (see the `staged_inputs` table above and
[`DET_TO_WORLD.md`](DET_TO_WORLD.md#readiness-and-staging-completion-gating))
rather than re-querying this view's underlying inventory. The view excludes
active `det_to_world` leases and successful `det_to_world` runs.

## Connection Behavior

`orchestrator.sqlite_db.open_db()` is the shared runtime connection helper.

Writable connections:

- create the database parent directory when necessary;
- use a 120-second connection timeout;
- enable foreign keys;
- store temporary objects in memory;
- configure a 120-second busy timeout; and
- use `synchronous=NORMAL`.

Read-only connections:

- require the database file to exist;
- enforce SQLite URI `mode=ro` and `query_only=ON`; and
- can query either the shared file directly or a temporary snapshot.

`submit.py` uses direct reads by default. Set `paths.db_read_mode: snapshot` to
create a consistent SQLite backup in a unique temporary file instead;
`paths.db_temp_dir` selects its location. The snapshot is deleted when its
connection closes.

The schema and runtime write helper both configure write-ahead logging.

## Transactions and Write Coordination

SQLite allows multiple readers but serializes writers. The orchestrator uses a
long busy timeout so short concurrent writes can wait rather than fail
immediately.

Two operations explicitly use `BEGIN IMMEDIATE`:

- claiming a stage lease; and
- creating or reopening an input-staging request.

These operations must atomically inspect existing state before writing new
state. Other status updates and lease metadata updates use short transactions
and commit immediately.

Operators should avoid applying schema changes, rebuilding large inventory
scopes, or manually modifying control tables while staging, polling, or compute
submission commands are writing to the same database.

## Applying and Inspecting the Schema

Apply or refresh the schema:

```bash
sqlite3 <database.sqlite3> < schemas/sqlite/pipeline.sql
```

Show the schema version:

```bash
sqlite3 <database.sqlite3> 'PRAGMA user_version;'
```

List tables and views:

```bash
sqlite3 <database.sqlite3> \
  "SELECT type, name FROM sqlite_master WHERE type IN ('table', 'view') ORDER BY type, name;"
```

Check foreign-key integrity:

```bash
sqlite3 <database.sqlite3> 'PRAGMA foreign_key_check;'
```

Check general database integrity:

```bash
sqlite3 <database.sqlite3> 'PRAGMA integrity_check;'
```

Run integrity checks when no inventory or orchestration writer is active.

## Read-Only Inspection Queries

These queries are diagnostic. Normal lifecycle changes should be performed by
the Python commands rather than manual SQL.

### Recent inventory runs

```sql
SELECT
    run_id,
    site,
    data_state,
    storage_root,
    status,
    total_files_seen,
    total_errors,
    started_at_ts_iso,
    ended_at_ts_iso
FROM inventory_runs
ORDER BY run_id DESC
LIMIT 20;
```

### Current inventory count by scope

```sql
SELECT
    site,
    data_state,
    storage_root,
    COUNT(*) AS current_entries
FROM globus_file_index
WHERE is_current = 1
GROUP BY site, data_state, storage_root
ORDER BY site, data_state, storage_root;
```

### Ready batches

```sql
SELECT *
FROM v_batches_needing_raw_to_jpg
LIMIT 20;

SELECT *
FROM v_batches_needing_jpg_to_det
LIMIT 20;
```

### Input-staging state

```sql
SELECT
    batch_id,
    stage,
    status,
    globus_task_id,
    requested_at,
    updated_at,
    error_summary
FROM staged_inputs
ORDER BY updated_at DESC
LIMIT 50;
```

### Active and expired leases

```sql
SELECT
    batch_id,
    stage,
    orchestrator_id,
    slurm_job_id,
    claimed_at,
    expires_at,
    CASE
        WHEN expires_at > strftime('%Y-%m-%dT%H:%M:%SZ', 'now')
        THEN 'active'
        ELSE 'expired'
    END AS lease_state
FROM stage_leases
ORDER BY expires_at;
```

### Recent stage runs

```sql
SELECT
    run_id,
    batch_id,
    stage,
    status,
    exit_code,
    n_units_succeeded,
    n_units_failed,
    ended_at
FROM stage_runs
ORDER BY ended_at DESC
LIMIT 50;
```

### Completed input gate for one stage

```sql
SELECT DISTINCT batch_id
FROM staged_inputs
WHERE stage = '<stage>'
  AND status = 'completed'
ORDER BY batch_id;
```

## Mutation Ownership

Use the supported commands for state changes:

| State change | Command or component |
| --- | --- |
| Refresh inventory | `scripts/admin/globus_index.py` |
| Create and submit input staging | `scripts/job/stage_inputs.py` |
| Refresh input-transfer status | `scripts/job/poll_stage_inputs.py` |
| Claim leases and record Slurm IDs | `orchestrator/submit_jobs.py` through `scripts/job/submit.py` |
| Ingest stage results and release leases | `scripts/job/ingest_and_release.py` |

Avoid manually inserting, updating, or deleting orchestration rows during
normal operation. The Python helpers enforce status validation, idempotency,
ownership checks, timestamp updates, and transaction boundaries that ad hoc SQL
can bypass.

## Schema Evolution

The schema uses:

```sql
PRAGMA user_version = 4;
```

When changing the schema:

1. Update `schemas/sqlite/pipeline.sql`.
2. Increment `PRAGMA user_version` for a new schema version.
3. Define how existing database files move to the new structure.
4. Update `scripts/admin/globus_index.py` if inventory columns or summaries
   change.
5. Update `orchestrator/sqlite_db.py` if orchestration columns, constraints, or
   statuses change.
6. Update readiness queries and their focused tests together.
7. Validate the new schema against both a fresh database and an upgraded copy.

Reapplying the current schema safely creates missing tables and indexes and
replaces readiness-view definitions. It does not provide a general migration
mechanism for altering existing table columns or constraints.
